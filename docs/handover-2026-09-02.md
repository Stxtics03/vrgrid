⚑ The training loss fell 0.167 → 0.1425 across the run. That is exactly why

**4. Ring 0 has no ρ on any sequence — DIAGNOSED 3 Sep, and the reason above
was wrong.** This item previously read "excludes footprints holding a single
reference *return*, and at 5 cm essentially all of them do." Both halves are
false. `block_stats` counts observed **cells**, not returns, and a ring-0
footprint is `k = 1` — exactly one cell — so `n_ref` can never exceed 1 and
`coarsening_ratio_per_ring`'s `n_ref > 1` guard drops ring 0 **by arithmetic,
on every sequence**. The data is there: M\* holds more than one return in
**92.8 / 97.0 / 97.4%** of the ring-0 cells §9.2 scores on 00 / 07 / 08 (median
6–12 returns), and a single HDL-64E sweep already puts >1 return into 57–66% of
the 5 cm columns inside 10 m. M\* sums those returns but discards the sum of
squares, so the within-cell spread that would give ring 0 a ρ is computed at
build time and thrown away.

Closing it would score ring 0 at **ρ 1.01–1.24 — the best of any ring on all
three sequences.** It is deferred rather than done because `block_stats` is
shared: the same change moves ring 1 by **−21.5%** on 07 and −7.5% on 08 (rings
2–3 under 2.3%), invalidates every cached M\* `.npz`, forces a regeneration of
the eleven-sequence table and the "ρ median 1.45" headline, and reaches
`plan_regret.costmap_from_reference`. Every ρ moves in the direction that
flatters us.

**So: a fixable gap with a measured cost, deliberately deferred to Day 7 — not
a permanent limitation.** Full diagnosis, tables and the narrower-variant
trade-off in `docs/known-limitations.md` §2b.

**2. The FRNet port works.** ~15% → **98.3%** point accuracy, **69.8%** mIoU
against the paper's 73.3%. Three fixes. **Divergences 2 and 3 were the two the
old header described wrongly; divergence 1 it got right** — corrected in the
port's own header and in `perception-dashboard-summary.md` §3 on 3 Sep:

- **1, right as written.** activation `nn.LeakyReLU` → `nn.Hardswish` at 7
  sites in `frnet_backbone.py` (mmcv HSwish is `x·relu6(x+3)/6`, which *is*
  `nn.Hardswish`);
- **2, wrong place.** The FOV bug was **not** in `frnet.py`, which always
  defaulted correctly to 3.0 / −25.0 — `semantics.py` was overriding it with
  the HDL-64E's *physical* FOV (2.0 / −24.8) out of `configs/frnet.yaml`. Two
  different quantities: the checkpoint learned a FIXED projection. Now pinned
  as `FRNET_TRAIN_FOV_*` constants a sensor config cannot reach;
- **3, understated.** `range_interpolation` was called "a missing
  densification (H=64, W=2048)", which reads as a resolution setting. It is a
  *test-pipeline transform to reproduce verbatim*, and it projects with the
  divergence-2 FOV — the two were coupled. Transcribed from upstream including
  an off-by-one (`proj_idx > 0`, so point index 0 reads invalid against a −1
  sentinel) reproduced **deliberately**, because the paper's 73.3% was measured
  with it and "fixing" it makes our numbers incomparable.

Two further factual corrections to that header: it said "413/413 tensors, no
shape mismatch" where the checkpoint loads **421, 0 missing and 8 unexpected**
(all `auxiliary_head.*`, training-only, correctly unused at inference); and it
named `frustum_encoder.py`'s manual `scatter_max`/`scatter_mean` as a suspected
fourth cause — they were not one, and that file is unchanged.

This is your module. It is reported alongside the map and never swapped into
it — semantics still come from the `.label` files so the mapping contribution
stays isolated.

**3. Patchwork++ is installed but not reproducibly.** `pip install
